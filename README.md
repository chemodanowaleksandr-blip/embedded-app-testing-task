# Тестовое задание: Тестирование распределенной системы управления (TCP)

Решение тестового задания на позицию QA Automation / Тестировщик встроенных систем.

## Часть 1. Чек-лист для проверки приложения (до 15 пунктов)

### Функциональное тестирование и UI
* **Проверка исходного состояния:** Запуск приложения без активного подключения к симулятору (таблица пустая, кнопка «Обновить» заблокирована).
* **Успешное подключение:** Нажатие на кнопку «Подключиться» при работающем симуляторе на порту 2001 (статус «Подключено», начинается прием сигналов).
* **Отображение таблицы:** Валидация наличия всех 5 колонок (ID, имя, значение, качество, время) и корректности рендеринга данных.
* **Ручное обновление:** Нажатие на кнопку «Обновить» мгновенно актуализирует данные на основе последних пакетов из сокета.
* **Корректность типов данных:** Проверка, что ID — целое число, время в валидном формате, а значение меняется (синусоида/random).

### Сетевое взаимодействие (TCP-сокет)
* **Отсутствие сервиса:** Попытка подключения, когда сервис-симулятор выключен (приложение не зависает, выводится ошибка Connection Refused).
* **Обрыв соединения:** Отключение симулятора после успешного коннекта (обработка потери сокета, статус качества меняется на "Bad").
* **Занятый порт:** Поведение системы, если порт 2001 уже занят другим процессом в ОС.

### Нагрузка, стабильность и негативные сценарии
* **Стресс-тест частоты:** Отправка пакетов с экстремально высокой частотой (UI не фризится, таблица обновляется корректно).
* **Некорректные данные (Bad Data):** Отправка через сокет поврежденных пакетов, пустых строк или null-значений (валидация на входе, приложение не падает).
* **Граничные значения:** Передача экстремально больших и маленьких числовых значений сигналов.
* **Цикличное переподключение:** Проверка отсутствия утечек памяти при многократном поочередном нажатии «Подключиться» -> разрыв.

## Часть 2. Критичный сценарий и автоматизация

### Выбор критичного сценария
**Сценарий:** Успешное подключение к TCP-сервису, получение пакета данных из 10 сигналов и валидация структуры данных в приложении.

**Обоснование:** Это главный позитивный сценарий (*Happy Path*) работы распределенной системы. Если приложение имеет баги в сетевом слое (не может поднять TCP-сессию) или некорректно парсит структуру пакета, вся остальная функциональность (интерфейс, кнопки, графики, логика управления) становится полностью неработоспособной.

### Запуск автотестов
Для симуляции работы TCP-сервера используется встроенная в тест фикстура, создающая mock-сервер в отдельном потоке.

**Команда для запуска:**
```bash
pip install pytest
pytest -v test_embedded_app.py
```
